# AMS — Evidence Analyst

Минимальный прототип для практического задания «Автономная система».

## Выбранное направление

**A — Доказательный аналитик.**

Система получает вопрос, строит ограниченный детерминированный план, ищет основания только среди документов, доступных текущей роли, и формирует ответ только на основе найденных фрагментов.

Если оснований нет, система явно отказывается от вывода.

## Стек

- Python 3.12
- Flask
- SQLite
- pytest
- Docker Compose
- HTML/CSS/JavaScript без frontend-фреймворка

Настоящая LLM не используется. Planner реализован детерминированно. Позже его можно заменить через тот же интерфейс на LLM-адаптер.

## Запуск

```bash
docker compose up --build
```

Открыть:

```text
http://localhost:5000
```

База SQLite создаётся автоматически в `data/app.db`.

## Тесты

Локально:

```bash
pip install -r requirements.txt
pytest -q
```

В контейнере:

```bash
docker compose run --rm evidence-analyst pytest -q
```

## API

### POST /tasks

Создаёт и выполняет задачу.

Пример:

```json
{
  "task_id": "11111111-1111-1111-1111-111111111111",
  "workspace_id": "demo-a",
  "user_id": "user-7",
  "role": "operator",
  "goal": "What is the data retention period?",
  "context": {},
  "mode": "read_only",
  "limits": {
    "max_steps": 3,
    "max_tool_calls": 1,
    "max_runtime_seconds": 10
  }
}
```

### GET /tasks/{task_id}

Возвращает состояние, результат, лимиты и trace_id.

### GET /tasks/{task_id}/events

Возвращает audit events в порядке создания.

## Архитектура

```text
Browser
   |
   v
Flask API
   |
   v
Planner
   |
   v
Retriever
   |
   v
Policy / Access Check
   |
   v
Answerer
   |
   v
SQLite
```

Planner не имеет прямого доступа к документам. Поиск выполняется отдельным модулем, а контроль workspace и role происходит до того, как фрагмент становится доказательством.

## Demo-сценарии

### 1. Два документа подтверждают факт

Два доступных документа содержат разные версии политики хранения. Они оба попадают в citations.

### 2. Документы противоречат друг другу

Для `What is the data retention period?` доступны версии с 30 и 60 днями.

Система не выбирает одну версию молча, а сообщает о противоречии и показывает обе версии источников.

### 3. Оснований нет

Для вопроса вроде:

```text
What is the server color?
```

нет подходящих фрагментов, поэтому система возвращает отказ.

### 4. Нет доступа к документу

`internal-1` доступен только роли `admin`. Для `operator` его фрагменты исключаются из поиска.

### 5. Повторный task_id

Повторная отправка существующего `task_id` получает HTTP 409 и не создаёт новую задачу.

## Ограничения

1. Поиск сделан простым lexical search, без embeddings/vector DB.
2. Planner детерминированный и не является настоящей LLM.
3. Документы demo заранее находятся в SQLite; отдельный upload API не реализован в минимальном MVP.
4. Выполнение задачи синхронное, что достаточно для demo.

## Угрозы

1. Неправильная настройка прав доступа может привести к выдаче закрытого документа.
2. Lexical search может не найти релевантный фрагмент из-за различий формулировок.
3. В production понадобились бы более строгая аутентификация, полноценная схема авторизации и отдельное хранилище документов.

## Следующие шаги

- добавить импорт TXT/Markdown через API;
- заменить lexical search на hybrid/vector retrieval;
- подключить реальную LLM через `Planner` adapter;
- добавить полноценную RBAC/ABAC-политику;
- вынести SQLite на PostgreSQL для production.
